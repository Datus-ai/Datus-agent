# Init

`init` 是初始化项目工作区的轻量方式。它读取项目里的 SQL 脚本、文档和数据库表结构，写下一份简洁的项目说明：该用哪些表、表之间怎么关联、有哪些规则必须遵守。这样后续会话一开始就带着写 SQL 所需的上下文，而不必构建较重的向量知识库。

在 REPL 中使用 `/init` 命令运行。

## 功能作用

- 用 `upsert_lineage` 工具把项目里的 SQL（ETL 脚本和 Python DAG 中的 SQL）静态分析成持久化的表级血缘图，再用 `query_lineage` 读取。关联条件、过滤条件、映射、窗口及作者注释从 SQL 原文读取。不执行任何 SQL。
- 阅读项目中人写的文档（业务规则、指标定义、数据字典）。
- 用数据库表结构核对找到的表和列：表清单、列信息，以及从建表语句里读出的声明主键和分区方式。它不查询表里的数据，所以不统计行数、新鲜度和编码的实际取值。
- 正式知识只写有来源明确说明的内容：建表语句、文档、SQL 注释、脚本实际做了什么、调度配置；粒度、主键、关联基数和表的地位都会注明出处。需要推断才能得出的结论，比如从 `GROUP BY` 推出的粒度、哪个版本是当前版本，会单独保存在 `knowledge/pending-questions.md` 中，明确标为未确认；回复只列出重要问题。问答 SQL 样例中明确的术语和字段映射可以注明来源后记录；推广到更大范围的解释仍作为待确认问题。
- 在项目根目录写一份 `AGENTS.md`：数据架构、核心表、跨业务域的规则，以及知识索引。
- 每个业务域写一个 `knowledge/<domain>.md`：表卡片（用途、粒度、时间、编码、必带过滤）、关联关系、血缘、指标定义、业务规则，以及已知问题（例如文档和数据库对不上的地方）。

它属于**轻量**层级。REPL `/init` 复用当前聊天会话，在一个受上下文容量和运行预算约束的普通 Agentic loop 中持续完成初始化；已有 metadata KB 时可以搜索候选表，不自动触发 metadata bootstrap。需要向量知识库时，请使用 [`/build-kb`](build_kb.md)。

血缘图保存在 `lineage/lineage.json`，整个项目共用一个文件。每个被分析的文件（或保存下来的一段 SQL）是一个来源：`upsert_lineage` 只重新分析内容、方言、默认库或解析器版本有变化的来源，并整份替换这个来源之前贡献的内容，所以 SQL 里删掉的语句，对应的血缘也会消失。方言和默认库作为项目设置保存在文件里，之后的调用不传这两个参数时，仍按同样的设置分析。`prune_missing=True` 会同时清理源文件已删除的来源，`delete_lineage` 可以按来源 ID 或 glob 删除。文件分四部分：`settings`（方言和默认库）、`sources`（内容 hash、方言、默认库、解析问题）、`nodes`（表、视图，以及代表纯查询的 `query:<hash>` 节点，`label` 取自作者注释）和 `edges`（上游 → 下游，每条边带着产生它的语句：来源、行号、加载方式和折叠的临时表；不读任何表的写入没有上游）。来源 ID 相对于项目根目录。文件里只有从 SQL 推导出的内容，没有时间戳或计数器，可以提交到版本库；如果合并后文件无法解析，可以用 `upsert_lineage(paths=[...], rebuild=True)` 从 SQL 文件重建。

`query_lineage` 返回指定表周围的子图（不传表则返回整张表级图）：每条语句一条记录，出处格式为 `文件ID:行号`，并给出每张表的角色、所属连通子图，以及有多少条已保存的查询读取它。`complete=false` 表示可能涉及所查表的来源（包括没有被任何返回语句引用的来源）在分析后有改动、是按其他设置分析的，或有语句没能解析。

在 `normal` 权限模式下，`upsert_lineage` 和 `delete_lineage` 写 `lineage/lineage.json` 前会先询问；`auto` 模式下 `upsert_lineage` 直接执行，`delete_lineage` 仍会询问。

**不兼容的变化：** `extract_sql_lineage` 由 `upsert_lineage`、`delete_lineage` 和 `query_lineage` 取代。血缘工具不再返回关联关系：init 从 SQL 原文读取关联条件，只有关联条件覆盖了声明的主键或唯一键的全部列时才写基数；脚本只是暗示的基数会作为待确认问题列出。参数条件不证明增量加载，单独的 ROW_NUMBER 定义也不证明表粒度。

## 何时使用

- 新项目工作区还没有 `AGENTS.md`。
- 你明确想要初始化或重新扫描项目。
- 脚本、文档或表结构有较大变化，项目说明已过时。

当一份最新的 `AGENTS.md` 已存在且没有实质变化时，可以跳过它。

## 如何使用

```text
/init
```

你可以在命令后附加自由文本提示——一个目标、一个范围，或要重点关注的文件 / 表：

```text
/init focus on the sales and finance schemas
```

不带提示时，`init` 从文档、SQL 输出表和相关血缘中选择当前数据源的核心表，优先探索；带提示时，只更新 `AGENTS.md` 和 knowledge 文件中范围内的部分。完成报告会明确本轮范围，不把核心范围完成当成全库完成。

`/init` 只接收可选的范围说明：

```text
/init 订单域，重点分析 orders 和 customers
/init
```

一次 `/init` 在当前普通 chat session 的一个 Agentic loop 中完成。模型按业务主题自主推进，运行时不会按业务域或表组反复启动新会话，也不会达到限制后重置预算续跑。没有固定表数上限；使用已有可配置的 `max_turns` 和工具超时。成功的 metadata 查询在本轮缓存复用。失败后可以根据新信息修正并重试，仍受本轮总预算和工具超时限制。完整 init skill 随本轮系统提示注入，自动压缩后仍然有效，退出后恢复普通聊天。

先读取已有 `AGENTS.md`、相关 knowledge、待确认问题、文档、SQL 和 lineage。大库缺少范围线索时通过 `ask_user` 请用户指定 schema、业务域或表清单。中途澄清保留已有成果和其他进度，用户最新修正优先。Init 不自动 bootstrap metadata；可以搜索已有 KB，但隐藏样本行。结构核对只用 metadata，DDL 按需读取，不查询业务数据。

工作步骤复用 `todo_list/read/write/update`，使用 todo 不开启 plan mode，也不要求确认计划。`plan_init_scope` 只登记或调整选定表、来源文件和未覆盖范围，没有分组、队列或结束当前聊天的语义。依赖表查询不自动扩大选定范围。`get_init_status` 有界读取范围、来源和用户澄清；这些记录不构成第二份执行计划。

模型通过普通文件工具增量维护 `AGENTS.md` 和 `knowledge/*.md`，保留人工内容、其他范围和已有有效定义。先写详情，再更新导航并读回检查。结构问题优先用工具查清；只有业务含义不明或工具无法取得的信息才留待用户确认。用途、粒度或 SQL 相似不能证明字段和键相同，结论必须对应实际证据。待确认问题保存在 `knowledge/pending-questions.md`，不能直接用于问答、SQL 或 build-kb 生成。

`report_init_progress` 记录摘要、明确完成的表、剩余工作和下一步，不结束 loop。查询结构成功不等于初始化完成；重复查询不会覆盖已报告的知识完成状态。文件类工作可以没有表，需要明确报告完成了什么。只有模型明确报告 `scope_complete=true`、没有选定表未完成，且运行正常结束，才记为选定范围完成。剩余工作文字用于保留上下文，填写“无”等说明不会覆盖完成标记；空计划、0/0 和普通回复都不会自动判成功。程序不认证知识正确，也不宣称全库覆盖。

大结果完整归档，通过 `read_tool_result` 分页读取，分页预算随可用模型窗口调整，并设有上限。必要时自动 mid-turn compact，保留目标、最新修正、完成情况和下一步，在同一 loop 中继续。进度详情按需读取，不反复注入全量表名单。容量检查包含完整输入、输出预留和安全余量；压缩不重置任务预算。中断、工具超时、模型错误或预算耗尽时保留文件，报告具体原因和剩余范围。正常结束或异常后，普通聊天恢复原有工具和交互，用户可继续确认待解决问题。

压缩时，程序在摘要旁保留有限条最近归档的完整编号、section 和分页游标，避免依赖模型转述这些编号。

没有 init 任务 ID、持久化任务队列或 `.datus/init/` 断点目录。后续 `/init` 重新读取已有文档补充知识。显式选择的 plan mode 仍按已有只读规则运行。文件权限和并发编辑沿用公共机制，没有 init 专用内容审核或跨文件事务。

## Init 与 Build KB 的区别 { #init-vs-build-kb }

| | `init` | [`/build-kb`](build_kb.md) |
|---|---|---|
| 速度 | 数分钟 | 更长 |
| 产出 | `AGENTS.md` + `knowledge/*.md` | 向量知识库：语义模型、指标、参考 SQL |
| 确认 | 范围不明时询问 | 生成清单确认门 |
| 向量索引 | 否 | 是 |
| 时机 | 最先、总是先做 | init 之后，当你需要语义检索时 |

典型流程：先运行 `/init` 获得即时上下文，需要向量索引知识库时再运行 `/build-kb`。

## 注意事项

- knowledge 以 markdown 文件存放在 `knowledge/` 下，由 `AGENTS.md` 索引；每个会话只加载 `AGENTS.md` 的前 200 行，所以细节放在 knowledge 文件里。
- 文档、SQL、数据库三者不一致时，`init` 会把冲突记在对应业务域的"已知问题"里，而不是悄悄选一边。
- `init` 只读取表结构元数据（表清单、列信息、建表语句），从不对表数据执行 `SELECT`。
- 待确认问题可以继续在对话里回答。你确认的内容会写进 knowledge 文件或 `AGENTS.md`，并注明由你确认；被否定的内容会丢弃。未确认问题按业务域保存在 `knowledge/pending-questions.md`，附上相关表和来源。模型发现问题时就用普通文件工具补充清单，保留其他业务域和人工内容。当前任务和后续聊天都能通过 `AGENTS.md` 中的链接找回；清单较长时搜索、分段读取。确认后更新正式知识，并只删除或标记对应问题已解决。清单明确属于未确认材料，不能直接作为问答、SQL 或 build-kb 生成的事实依据；没有问题时不必创建。
- 生成语义模型、指标和参考 SQL 是 [`/build-kb`](build_kb.md) 的职责。
