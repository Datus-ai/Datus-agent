# `/init` 当前实现：流程、大库优化、工具与测试

更新日期：2026-10-26。实现基线：PR [#1540](https://github.com/Datus-ai/Datus-agent/pull/1540)，工作区在 `53b0d60c2` 基础上移除了专用进度工具。这里记录已实现的行为；真实模型测试使用各次运行保存的源码快照，不能视为对最新提交的完整实测。

## 1. 现在的执行方式

`/init` 的目标是把项目资料和数据库结构整理成后续问答、写 SQL 能用的项目知识。它通过普通 chat 加载 init skill，在**当前聊天会话的一个 Agentic loop** 中完成。

```text
/init [自由文本范围]
  → 绑定当前项目、数据源、catalog / database / schema
  → 在当前 chat 中加载 init skill，临时启用 init 工具边界
  → 阅读已有知识、文档、SQL，确定本轮范围
  → 模型自主选择业务主题、查结构、分析来源
  → 增量写知识，更新 todo 和完成情况
  → 大结果按页读取；上下文不足时自动压缩，再继续当前任务
  → 正常完成，或报告停止原因和未完成范围
  → 恢复普通聊天工具，继续接受用户确认与补充
```

一个 loop 可以包含多次模型调用、工具调用和自动压缩。程序不按表组反复启动 chat，也不在预算耗尽后另起会话续跑。没有固定表数上限、业务批次队列或 init 专用断点目录。

主要入口是 [init_commands.py](../../datus/cli/init_commands.py)，实际执行复用 [chat_commands.py](../../datus/cli/chat_commands.py)，探索和知识整理规则来自 [init skill](../../datus/resources/skills/init/SKILL.md)。

## 2. 用户会经历什么

### 发起和确定范围

```text
/init
/init 订单域，重点分析 orders 和 customers
/init 补充财务域，保留已有订单域说明
```

命令后的内容是自由文本，不解析 `--batch-size`、`--max-tables`、`--resume` 等 init 专用参数。运行预算使用已有的 `max_turns` 配置，超时沿用各工具设置。

- **用户给了范围**：围绕指定的文件、表或业务域探索，增量维护相应知识。
- **用户没有给范围**：模型先看已有 `AGENTS.md`、knowledge、文档、SQL 输出表和相关血缘，寻找有证据支持的核心范围。
- **表很多，又没有可靠线索**：通过 `ask_user` 请用户指定 schema、业务域或表清单。不会为了凑数量随意选“核心表”。取消澄清会停止本轮，保留已有成果。
- **分析中发现依赖表**：模型可以继续查相关结构、搜索 metadata、更新血缘。程序不把初始表清单当作工具访问白名单；数据源边界仍然有效。

核心范围由模型结合资料和用户目标判断，不是程序根据表名、表大小或图的连接数算出的固定排名。

### 探索和写入

1. 读取已有知识、相关待确认问题及项目资料，避免重复整理或覆盖人工内容。
2. 当前提供 `search_table` 时，尝试搜索已有 metadata KB 找候选表；工具不可用或未命中时可直接查元数据。工具可用不代表索引完整或最新。**init 不自动执行 metadata bootstrap**，也不先收集全库 DDL。
3. 用 `list_tables`、`describe_table` 核对相关表和字段；重要的键、约束、分区等信息按需读 `get_table_ddl`。
4. 用 `upsert_lineage` 静态解析范围内的 SQL，再用 `query_lineage` 查看关联语句；公式、过滤和关联条件仍回到 SQL 原文核对。SQL 不执行。
5. 模型通过普通文件工具边分析边写入知识，并读回检查。工作步骤由已有 todo 工具管理，使用 todo 不会自动开启 plan mode，也不要求用户先批准计划。

结构问题优先通过工具查清。业务含义不明、来源不足或工具无法取得的信息，写入 `knowledge/pending-questions.md`；未完成的结构查询应报告为剩余工作。待确认内容不作为已确认事实使用。

### 中途交互和结束

用户可以沿用普通聊天的流式显示、中断和消息插入能力。最新修正、澄清答案与已有进度一起保留，压缩后继续使用。若 loop 已结束时还有未处理的插入消息，消息留给下一轮，不自动启动新 loop 重置预算。

结束时回复本轮范围、修改文件、已核对内容、重要问题和未完成部分，CLI 另显示执行状态、修改文件数及停止原因。正常结束、异常或中断后，恢复普通聊天的工具、MCP、内置 Web 工具和交互状态。

后续用户可以直接确认待解决问题，也可以再次 `/init 新范围`。新的初始化读取已有知识再补充；没有 `.datus/init/<run_id>/` 或专用断点续传。普通聊天本身仍有 session 和历史归档。

## 3. 产物和“完成”的含义

| 产物 | 内容 |
| --- | --- |
| `AGENTS.md` | 简洁的项目说明、重要跨域规则和知识导航；skill 要求控制在 200 行内 |
| `knowledge/<domain>.md` | 表用途、字段和键的依据、关联、指标、业务规则、来源与已知问题 |
| `knowledge/pending-questions.md` | 明确标为未确认的问题；保留其他业务域和人工内容，确认后更新对应知识 |
| `lineage/lineage.json` | 项目共用的表级 SQL 血缘，由血缘工具维护 |
| 普通 session 归档 | 历史和大工具结果，供分页与压缩恢复；不是一份全库知识摘要 |

普通文件写入只允许项目中的 `AGENTS.md` 和 `knowledge/` 下的 Markdown；血缘走专用工具。模型负责知识内容和增量编辑，程序检查路径、工具权限和运行状态，**没有 init 专用的业务内容认证器或跨文件事务**。

工作进度统一使用已有 `todo_list/read/write/update`，按业务主题组织；模型自行调整步骤，不要求每张表建任务。范围来自用户说明、澄清和当前工作计划，程序不维护第二份选定表清单或完成统计。

程序只记录执行状态：`returned` 表示本轮正常返回，`stopped` 表示异常、中断、预算耗尽或仍有未处理输入等停止情况，并保留原因。这些状态不认证知识完成度；todo 全部勾选也不代表整个数据库覆盖完成。文件类任务无需表清单。已经写下的文件在中断或错误后保留。

最终回复由模型说明实际处理的范围、成果、修改文件、待确认问题和未完成工作。`knowledge/pending-questions.md` 只记录待确认问题，不充当进度文件。压缩后从会话摘要、todo 和知识文件恢复工作；用户澄清过长时通过现有 `ToolResultStore` 分页恢复原文。

## 4. 为几万张表做了哪些优化

### 4.1 按目标探索，减少无关工作

模型决定读哪些资料、哪些表和哪些字段证据，运行时不强制全库遍历。已有 KB 可以搜索，相关血缘优先按表查询，DDL 按需读取。没有新增全库索引建设任务，也不把几万张表名反复塞进本地摘要或系统提示。

这能控制无关工作，但不保证任意范围都在几分钟内结束。范围越大、资料越复杂，模型调用和数据库访问仍可能越多。

### 4.2 大工具结果先保存，模型按页看

通用工具调用层保留完整结果；模型输入准备阶段通过 `ToolResultStore` 生成受限展示：

```text
list_tables / describe_table / query_lineage / grep 等原工具
  → 原始结果保留，较大的结果完整归档
  → 模型先收到受限内容、总量信息、result_id、section、分页游标
  → 需要更多时调用 read_tool_result，读取已保存的下一页
```

- 不需要给每个原工具另加一套分页接口，普通调用者和 ActionHistory 仍可取得原工具结果。
- `result_id` 是程序根据工具调用 ID 和结果内容哈希生成的归档编号，不由模型编造；归档属于当前 session。
- 表清单、列信息和血缘各部分可以分别分页。单条记录或单行 SQL 过长时，继续拆成可回读的文本片段。
- 分页同时限制条数、字节和 token 预算；页预算随模型容量调整，并有上限。页大小不是一次 init 允许处理的表数。
- 回读不会重新查数据库。来源本身已经截断的结果会保留截断/完整性标记，不能把“归档读完”解释为“来源查全”。

**边界：这是模型侧分页，不是数据库服务端分页。** `list_tables` 的原始接口仍可能一次取回全目录；它仍有数据库、网络、内存和首次归档开销。几万张表不会一次进入模型窗口，不等于列目录本身没有成本。

### 4.3 元数据缓存和直接定位 DDL

本轮成功的目录、表结构、DDL 和 metadata 搜索结果可以复用。相同有效表标识会共用缓存；并发重复请求串行处理，避免同时重复查库。失败结果不当成成功缓存，模型可根据错误修正参数后重试。

单表 DDL 曾在部分 adapter 中先拉全库目录再筛表。相关修复属于独立的 [datus-db-adapters PR #176](https://github.com/Datus-ai/datus-db-adapters/pull/176)：对存在该路径的 adapter 改为按目标定位。它减少数据库端开销，和 Agent 的归档分页各解决一层问题；需要安装包含修复的 adapter，不能仅凭 Agent PR 推定已生效。

### 4.4 每次发送前检查完整请求

通用 `RequestCapacity` 和模型适配器在发送前校验：

```text
完整输入 + 输出预留 + 安全余量 ≤ 模型窗口
```

完整输入包括系统提示、消息、工具定义等，不能只数用户文本。没有显式输出配置时，支持输出限额的模型先扣除安全余量，默认输出最多占剩余窗口的一半；显式配置和请求覆盖值仍需通过容量检查。不能限制输出的传输方式不能假装通过调小预留来获得更多输入空间。

例如窗口 `262144`、输出 `8192` 时，安全余量 `13108`，输入上限为 `240844`。计数方法会随模型/tokenizer 条件不同而不同；保守计数不能当作供应商返回的实际 token 用量。

小窗口也单独覆盖：窗口为 `4096`、安全余量为 `2048` 时，默认输出最多 `1024`，仍为输入留下 `1024`。普通图片聊天复用同一容量层时，从文本计数中去掉请求消息内的图片 base64，再按图片计数规则计入图片开销，保留原请求的 `low/high/auto` 清晰度设置，避免重复计算；发送给模型的原始图片不变。init 的工具白名单本身不因此扩大。

已有模型规格可用于解析容量，但不会自动探测任意私有部署的真实窗口。自部署别名需要准确的 `context_length`、`max_tokens` 和适用的 `tokenizer_ref`。规格或计数条件不足时会明确失败，不盲发超限请求。配置说明见 [模型容量配置](../configuration/agent.zh.md)。

### 4.5 同一 loop 自动压缩并继续

接近容量限制时，先缩减大结果展示，再通过 `MidTurnCompactor` 压缩历史。摘要请求过大时，`summary_chunks.py` 分块总结；摘要调用本身也受容量和调用数量限制。

压缩保留当前目标、最新用户修正、已完成/剩余工作和下一步。原始历史归档；有限条最近工具结果的完整 `result_id`、section 和游标由程序保留，避免模型在摘要中把编号缩写后无法回读。完整 init skill 持续注入本轮指令，压缩后不靠模型重新加载才能生效。

SDK 和 native 路径都同步压缩后的上下文。Claude native 路径还区分“仅给模型展示短结果”和“真正重写持久历史”，避免漏存新用户消息或插入消息。

压缩不重置当前 loop 的 `max_turns`。压缩后仍无法容纳请求、归档不可用、模型错误、中断或工具超时，会停止并保留已写成果。超时后仍在运行的底层任务会被跟踪，本轮不继续叠加探索请求。

## 5. 工具层面的改动

### 新增或调整的模型可见工具

| 工具 | 职责和边界 |
| --- | --- |
| `read_tool_result(result_id, section, cursor, limit)` | 通用新增工具，按页读取当前 session 已归档的结果；不能读取其他 session 或任意路径 |
| `todo_list/read/write/update` | 复用已有工具，负责工作步骤；不和 init 状态另建两份执行计划 |

init 不再新增专用进度工具。`read_tool_result` 是通用容量保护能力，工作规划和状态复用已有 todo 工具。

### 已有工具如何接入

| 工具或公共层 | 变化 |
| --- | --- |
| `list_tables` | 保留原接口；init 内缓存成功结果，大目录通过公共归档展示和回读 |
| `describe_table` / `get_table_ddl` | init 在工具集合缺少 `get_table_ddl` 时补充暴露这个已有方法；缓存成功结果，按方言解析限定名并核对数据库边界；大列清单、长 DDL 走通用归档 |
| `search_table` | 复用已有 metadata KB；init 会递归去掉样本数据，缓存和归档也使用清理后的结果 |
| `query_lineage` | 保留原查询语义；传表查相关子图，不传表仍可能返回全图。大图由通用层归档，血缘、节点等分别回读 |
| `upsert_lineage` | 沿用已有静态解析和持久化能力，分析过程中可调用；不是本次新增的工具 |
| 文件读取、`glob`、`grep` | 沿用已有工具；大返回和超长行由通用结果层处理，来源的截断信息保留 |
| `write_file` / `edit_file` | 模型直接增量编辑知识，init 包装层限制输出位置，沿用公共权限和编辑机制 |
| 公共参数解析 | 仅在 schema 明确要求数组或布尔值时，兼容被模型编码成字符串的数组/布尔值；保留正常字符串与严格校验，不在 init 内放 Qwen 专用分支 |
| 公共模型输入层 | 结果投影、发送前容量检查、分页阅读器、压缩及引用恢复，可供其他 Agentic 场景复用 |

init 只暴露必要的资料读取、只读元数据、知识写入、血缘更新、todo 和用户交互工具。通用 SQL、业务数据查询、样本行、shell、MCP 和委派工具不在本轮白名单中。工具刷新或压缩后会重新应用这些限制；退出时恢复原始工具面。

## 7. 目前能解决什么，还不能保证什么

现在可以在拥有几万张表的数据库中，围绕用户需要的范围持续初始化；大目录、宽表、长 SQL 和大血缘不会未经处理整份塞进模型上下文，任务可以在同一 loop 内压缩后继续。

仍需保留以下边界：

- 不保证一次 `/init` 整理完任意规模的全库，也没有确定的总耗时承诺。
- `list_tables` 仍可能有全目录获取成本；结果分页并未改变数据库查询方式。
- 自部署模型的窗口和 tokenizer 配置需要准确，不能从任意别名推断真实服务规格。
- 运行完成、结构查过、归档完整，都不等于知识解释一定正确。
- 最新实现仍需要更多真实模型重复验收，特别是多次压缩、中途用户修正和知识陈述与证据一致性的组合场景。
